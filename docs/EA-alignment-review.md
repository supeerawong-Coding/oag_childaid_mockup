# ผลตรวจความสอดคล้อง OAG ChildAid กับแผน EA และแผนดิจิทัล พ.ศ. 2569-2573

วันที่ตรวจ: 6 ตุลาคม 2569

## ข้อสรุป

**OAG ChildAid สอดคล้องกับทิศทางของแผนในระดับแนวคิดและต้นแบบกระบวนงาน โดยเฉพาะกลยุทธ์ 2.1 และ 2.2 แต่ยังมีช่องว่างด้านข้อมูลร่วม บริการกลาง ความมั่นคงปลอดภัย และการกำกับดูแล จึงยังยืนยันไม่ได้ว่าเป็นระบบที่สอดคล้องกับสถาปัตยกรรมเป้าหมายครบถ้วนหรือพร้อมใช้งานจริง**

ระบบเหมาะสำหรับทบทวนความต้องการและสาธิตงานคำปรึกษาเด็ก งานชั้นพนักงานอัยการ กิจกรรม และรายงาน ก่อนกำหนดสถาปัตยกรรมและมาตรฐานสำหรับการใช้งานจริง การเป็น mockup ไม่ใช่ข้อบกพร่องของต้นแบบ แต่ต้องแยกจากหลักฐานความพร้อมของระบบใช้งานจริง

## ประเด็นข้อมูลเด็กและการตีความรายงาน

1. `childrenFor` ใช้คีย์ชนิดงานร่วมกับรหัสเด็ก (`domain.mjs:75`) และ README ระบุไม่ตัดซ้ำข้ามคำปรึกษา/งานอัยการ จึงควรเรียกยอดนี้ว่า “เด็กตามงาน” หรือหน่วยที่กำหนดไว้ ไม่ใช้เป็น “จำนวนเด็กไม่ซ้ำทั้งองค์กร” โดยไม่มีวิธีระบุตัวบุคคลและกติกาที่ได้รับอนุมัติ การแยกเด็กตามงานไม่ได้ผิดโดยตัวมันเอง แต่ต้องแยกทะเบียนบุคคลออกจากข้อมูลการรับบริการหากต้องติดตามข้ามงาน
2. กิจกรรมนับผู้เข้าร่วมเป็นคน-ครั้ง ไม่ใช่จำนวนคนไม่ซ้ำ และข้อมูลเด็กในกราฟเป็นข้อมูลปัจจุบันของรายการ ไม่ใช่ภาพข้อมูล ณ เวลาย้อนหลัง (`README.md:34`) หากต้องวิเคราะห์การเปลี่ยนแปลงควรออกแบบประวัติข้อมูลและวันมีผล
3. schema มีข้อมูลระบุตัวบุคคล ที่อยู่ ข้อมูลครอบครัวและข้อมูลเด็ก ส่วน CSV ส่งออกชื่อเด็กและข้อมูลความบกพร่อง/การศึกษา/ครอบครัว (`main.tsx:1186`) ก่อนใช้ข้อมูลจริงควรกำหนดสิทธิส่งออก บันทึกการส่งออก และชุดรายงานที่ลดการระบุตัวบุคคลตามนโยบายขององค์กร
4. การเผยแพร่ข้อมูลสาธารณะตามยุทธศาสตร์ 1 ไม่ได้หมายถึงการเผยแพร่ข้อมูลเด็กหรือคดีรายบุคคล ควรออกแบบชุดสถิติรวมและกติกาป้องกันการระบุตัวบุคคลโดยเจ้าของข้อมูล
5. ตัวตรวจข้อมูลปัจจุบันช่วยเรื่องคุณภาพข้อมูลระดับแบบฟอร์ม แต่ไม่ทดแทนกติกาที่ backend และทะเบียนกลางเมื่อมีผู้ใช้หลายสำนักงาน

ข้อเสนอข้างต้นเป็นการออกแบบเพื่อปิดช่องว่างตามหลักข้อมูลและธรรมาภิบาลของแผน ไม่ใช่ผลตรวจรับหรือคำวินิจฉัยการปฏิบัติตามกฎหมายเฉพาะฉบับ

| SO-KPI 4.3.3 / TO-KPI 4.2.4 (7 / 11) | โครงการที่ผ่านการตรวจความสอดคล้อง EA/มาตรฐานกลางอย่างน้อย 90% | เอกสาร mapping สถาปัตยกรรม บริการที่ใช้ มาตรฐานที่เกี่ยวข้อง และผลทบทวนโดยผู้รับผิดชอบ |

เป้าหมายร้อยละและจำนวนบริการ/ระบบเป็นตัวชี้วัดระดับองค์กรตามเอกสาร ไม่ควรนำมาสรุปว่า ChildAid ต้องทำครบทุกบริการเอง หรือใช้ผล unit test เป็นหลักฐานบรรลุ KPI เหล่านี้

## ความสอดคล้องกับ Roadmap

จากภาพหน้าเอกสาร 15-18 / PDF 19-22:

- ปี 2569: MIS, OAG Tracking, Big Data และ Common Services เช่น Authen, Exchange, Search, Document, Notification อยู่ในแผนช่วงต้น
- ปี 2570: Data Governance, EA Governance และ ITSM อยู่ใน Roadmap
- ปี 2572: Intelligent Data Platform อยู่ใน Roadmap
- ปี 2573: Smart DSS และ IAM อยู่ใน Roadmap

ดังนั้น ChildAid ควรยืนยันการใช้บริการกลางและข้อมูลร่วมตั้งแต่การออกแบบ และเตรียมข้อมูลให้ส่งต่อแพลตฟอร์มข้อมูลในระยะถัดไป การไม่มี AI หรือ Smart DSS ในต้นแบบปัจจุบันเพียงอย่างเดียวไม่เพียงพอจะตัดสินว่าไม่สอดคล้องแผน เนื่องจากเป็นองค์ประกอบขององค์กรที่ทยอยพัฒนาต่างช่วงเวลา

แม้โครงการ IAM ใน Roadmap อยู่ปี 2573 แต่แผนยุทธศาสตร์ 4 กำหนดเรื่องการควบคุมสิทธิและธรรมาภิบาลไว้แล้ว การใช้งานข้อมูลจริงควรมีการยืนยันตัวตนและควบคุมสิทธิที่ใช้งานได้ตั้งแต่เริ่ม และออกแบบให้เชื่อม IAM กลางเมื่อพร้อม ไม่ต้องสร้าง IAM องค์กรใหม่ใน ChildAid

การวาง ChildAid เป็นโมดูล/ระบบงานภายใต้ชั้น Transaction Processing เชื่อม MIS/สารบบและ Common Services เป็น **ข้อเสนอจากการเทียบภาพสถาปัตยกรรม** ไม่ใช่ข้อความที่ระบุชื่อ ChildAid ไว้โดยตรงใน PDF ที่ตรวจ และยังต้องให้เจ้าของ EA ยืนยัน

## ลำดับงานที่แนะนำ

รายการต่อไปนี้เป็นข้อเสนอของการตรวจ ไม่ใช่กำหนดเวลาหรือ TOR ที่คัดลอกจากเอกสาร

### ก่อนเริ่มพัฒนาระบบใช้งานจริง

1. ยืนยันเจ้าของระบบ/ข้อมูล ตำแหน่ง ChildAid ใน EA และขอบเขตเชื่อม MIS/สารบบ/OAG Tracking ให้ชัดเจน พร้อมแผนภาพ As-Is/To-Be
2. ขอรายการบริการกลางที่ใช้งานได้จริง มาตรฐาน API/ข้อมูล/รหัสสำนักงาน และข้อกำหนดด้านสิทธิและการติดตั้งจากหน่วยงานเจ้าของระบบ
3. ยืนยันกระบวนงานกับเจ้าหน้าที่: ผู้รับเรื่อง ผู้รับผิดชอบ ผู้ตรวจ/อนุมัติ ขั้นตอนส่งต่อ และเกณฑ์ปิดงาน พร้อมกำหนด KPI และข้อมูลฐานก่อนใช้งาน

### ก่อนนำข้อมูลจริงเข้าระบบ

1. พัฒนา backend และฐานข้อมูลกลางที่บังคับสิทธิรองรับหลายสำนักงาน พร้อมจัดการรหัสกลาง ความถูกต้องและการแก้ไขข้อมูลพร้อมกัน
2. เชื่อมการยืนยันตัวตนที่องค์กรอนุมัติ และกำหนดสิทธิอ่าน/แก้ไข/อนุมัติ/ส่งออกตามบทบาทและขอบเขตสำนักงาน
3. เพิ่ม Audit Log ที่บันทึกอัตโนมัติ แยกจากประวัติขั้นตอนที่ผู้ใช้กรอกเอง
4. กำหนดชั้นข้อมูล สิทธิรายงาน การลดการระบุตัวบุคคล อายุเก็บรักษา และกระบวนการใช้/ส่งออกข้อมูลเด็กตามนโยบายองค์กร
5. วางสถาปัตยกรรมติดตั้งและมาตรการป้องกันข้อมูล แผนสำรองและกู้คืน เชื่อมระบบเฝ้าระวัง และมีผลทดสอบก่อนเปิดใช้

### ก่อนขยายใช้งานและรายงานผลตามแผน

1. ทดสอบเชื่อมระบบกลางจริง รวมกรณีส่งต่อสำเร็จ/ล้มเหลวและข้อมูลซ้ำ โดยใช้ข้อมูลทดสอบ
2. ทำ UAT หลายบทบาท/สำนักงาน อบรมเจ้าหน้าที่ และจัดทำคู่มือพร้อมช่องทางสนับสนุน
3. เก็บเวลา สถานะและการใช้งานเพื่อวัด KPI จากข้อมูลจริง พร้อมแยกยอดคน/คน-ครั้ง/เด็กตามงานให้ชัดเจน
4. ส่งผลการออกแบบและหลักฐานทดสอบให้ผู้รับผิดชอบ EA ตรวจตามมาตรฐานองค์กรก่อนสรุปว่า “ผ่าน EA”

## หลักฐานที่ยังต้องขอเพื่อยืนยันผลอย่างเป็นทางการ

- แบบ EA ฉบับรายละเอียดและมาตรฐานกลางที่อนุมัติใช้ รวมข้อกำหนดเฉพาะของระบบนี้
- ขอบเขตโครงการ/TOR หรือรายการความต้องการที่อนุมัติ พร้อมเจ้าของกระบวนงาน
- แบบเชื่อมสารบบ/MIS/บริการกลาง รวม API และแบบข้อมูล
- นโยบายข้อมูลและสิทธิที่ใช้กับข้อมูลเด็กและคดี
- สถาปัตยกรรม deployment, แผนสำรอง/กู้คืน และผลประเมินระบบจริง
- ผล UAT, การอบรม, ผลวัด KPI และหลักฐานทบทวน EA

## ข้อความเสนอสำหรับสรุปต่อผู้บริหาร

> ระบบ OAG ChildAid มีทิศทางสอดคล้องกับแผนปฏิบัติการดิจิทัล พ.ศ. 2569-2573 โดยสนับสนุนการปรับกระบวนงานและการจัดทำข้อมูลเพื่อการบริหารในระดับต้นแบบ อย่างไรก็ตาม ก่อนนำไปใช้งานจริงจำเป็นต้องกำหนดการเชื่อมข้อมูลและบริการกลางขององค์กร การควบคุมสิทธิ บันทึกการตรวจสอบ ธรรมาภิบาลข้อมูล และความพร้อมด้านโครงสร้างพื้นฐาน รวมทั้งจัดทำหลักฐานผลการใช้งานและผ่านการทบทวนตามกรอบ EA ขององค์กร
